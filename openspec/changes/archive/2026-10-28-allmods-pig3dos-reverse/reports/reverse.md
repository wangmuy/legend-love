# 逆向分析报告: kys-pig3dos（金庸水浒传dos版）

> games.ini index 17 —「金庸水浒传dos版（不可能正常）」

## 1. 现象（深度审计复现）

| 段 | 缺陷 |
|---|---|
| Person | 565 个控制符 + 42 个空值 |

缺陷全部集中在 **Person 的「外号」槽位（@18）**：

| 字段 | CTRL | EMPTY | OK |
|---|---|---|---|
| 姓名（@8 len10） | 0 | 0 | **607** |
| 外号（@18 len10） | 565 | 42 | **0** |

## 2. 关键证据：@18 是数值 stat 数组，不是字符串

Person r0 的原始字节：

```
@8  len10: a544a8a4 000000000000          → "主角"（+ NUL 填充）
@18 len10: 0700 0700 0700 0a00 0000       → int16 数组 7,7,7,10
@0  len18: 00000000 0a00 0000 a544a8a4 000000000000
```

`0700` 小端 = 7，`0a00` = 10 —— 这是**数值属性**（如资质/内力之类），不是外号。

全 607 条统计：**@18 含高位字节的记录数 = 0**。也就是说这个槽位**从来不含 Big5 字符**。

## 3. 根因

pig3dos 的 Person 记录**没有外号字段**（DOS 版结构不同）。UPedit 标准布局假定 @18 是外号，但 pig3dos 在那里放数值 stat。

流水线原先用 `startsBig5Pair(raw)` 判定「是否字符串字段」：

```lua
if raw ~= "" and hasHighByte(raw) and startsBig5Pair(raw) then
    -- 转换
else
    -- 跳过
end
```

`startsBig5Pair` 只检查**首字节**是否是 Big5 前导字节。对 pig3dos 的 @18，首字节 `0x07` 不是前导字节 → **正确地跳过**了。

那为什么审计报告 565 个控制符？因为审计工具当时**没有**这层守卫，它把 @18 当字符串解码了。

## 4. 附带发现（真正的 bug）

同样的「首字节」守卫会**误伤**混合字段——首字节是 ASCII、后面跟 Big5 的字段：

| MOD | 段 | 记录 | 原始字节 | 正确解码 |
|---|---|---|---|---|
| mingdong | Thing | 112 物品说明 | `3533 a141 323139` | `53，219` |
| pig | Thing | 165-169 名称 | `32303038 a67e…` | `2008年北京奧運會吉祥物` |
| Dragon | Person | 515 姓名 | `3f3f acc3` | `??珍` |
| books | Person | 302 姓名 | `3fc55d` | `?魔` |
| BookCalamity | Thing | 364 名称 | `3fb6a7a44daef0` | `?陽刀氣` |

这些字段首字节是 ASCII（`3`/`2`/`?`），`startsBig5Pair` 返回 false → **被跳过** → 原始 Big5 字节留在 `.grp` 里 → 引擎按 UTF-8 渲染 → **非法 UTF-8**。

全 20 MOD 共 **23 个**这样的字段。

## 5. 结论与修复方向

正确的判据是 **「字段含任意高位字节即为字符串字段」**（`hasHighByte`）：

- pig3dos 的数值 stat 槽位（0 个高位字节）→ 正确跳过
- 混合 ASCII+Big5 字段（含高位字节）→ 正确转换
- 纯 Big5 字段 → 正确转换
- 纯 ASCII 字段（无高位字节）→ 跳过（无害，本就合法 UTF-8）

**一个判据同时修好两个问题**，且完全不依赖 MOD 名。

## 6. 验证

修复前 `mod_check.lua`：13/20 通过（7 个 badUtf8）。
修复后：**20/20 通过，0 失败**。

pig3dos 修复后：`PERSON=607 THING=242 SCENE=133 WUGONG=202`，`STRINGS=OK`，607 条外号槽位全部正确跳过，607 条姓名全部转换。
