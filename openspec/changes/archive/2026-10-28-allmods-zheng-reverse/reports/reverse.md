# 逆向分析报告: kys-zheng（魏征传奇）

> games.ini index 9 —「魏征传奇（好像不太正常）」

## 1. 现象（深度审计复现）

用逐字段审计（不复用 `mod_check_one.lua` 的浅层自检）扫描 zheng 的 `save/ranger.grp`：

| 段 | 缺陷 |
|---|---|
| Thing | 196 个 U+FFFD + 47 个控制符 |
| Scene | 54 个空值 + 24 个控制符 |
| Wugong | 214 个空值 |

`mod_check_one.lua` 当时**全部报 OK**——它是浅层自检，只抽查前 400 条记录的首个字段，会漏报。

## 2. 关键证据：zheng 的 ranger.grp 与 pascal 逐字节同头

```
zheng  ranger.grp: 114242 字节
pascal ranger.grp: 114242 字节

zheng [0..16]: 000000006501eb002d001d0001006d00
pascal[0..16]: 000000006501eb002d001d0001006d00   ← 完全相同
```

两者大小相同、头部相同 → **zheng 的 ranger.grp 布局就是标准 UPedit 布局**。

## 3. 根因：zheng 的 ranger.idx 描述的是另一个文件

```
zheng ranger.idx  末值 = 138596
zheng ranger.grp  大小 = 114242
```

zheng 的 `save/` 目录里同时存在：

| 文件 | 大小 |
|---|---|
| `ranger.grp` | 114242 |
| `r4.grp` | 114242 |
| `r5.grp` | 114242 |
| `r1.grp` | **138596** |
| `r6.grp` | **138596** |
| `r11.grp` | **138596** |
| `ranger.idx` | 24 字节（末值 138596） |

**出厂 idx 取自 138596 字节的存档（`r1.grp`/`r6.grp`/`r11.grp`），而不是 114242 字节的 `ranger.grp`。**

用损坏 idx 推导出的段记录数（358/201/94/216）与实际不符，于是：

- Thing 段被拉长，越过真实边界读到 Scene 数据 → 196 个 U+FFFD
- Scene 段起点错位 → 54 个空值
- Wugong 段起点错位 → 214 个空值

## 4. 验证：正确 idx 下 zheng 完全干净

用标准布局 `836,59076,97076,101444,114092,114242` 解码 zheng：

| 段 | 记录数 |
|---|---|
| Person | 320 |
| Thing | 200 |
| Scene | 84 |
| Wugong | 93 |
| Shop | 3 |

抽样解码：

| 位置 | 值 |
|---|---|
| `Person[0].姓名` | 小蝦米 |
| `Person[0].外号` | 天下奇男子 |
| `Thing[0].物品名` | 康倍特 |
| `Scene[0].名称` | 胡斐居 |
| `Wugong[0].名称` | 普通攻擊 |

**全部零 U+FFFD、零空值、零控制符。**

## 5. 结论

**zheng 从未结构损坏，只是 idx 损坏。** 此前「复合布局」理论（Thing 探测出 116/136/156 等）是 idx 损坏造成的红鲱鱼：损坏 idx 让探测算法在一个错位的物理区域内搜索，从而拟合出看似合理的「非标准」偏移。

修复方向：**构建期从 `ranger.grp` 字节推断正确分段边界，产出正确 idx**，不改源数据、不改运行时。

## 6. 全 20 MOD idx 一致性扫描

| MOD | idx 末值 | grp 大小 | 一致？ |
|---|---|---|---|
| pascal | 114242 | 114242 | ✓ |
| Dragon | 174228 | 174230 | ✓（2 字节尾部 padding）|
| …（16 个）| — | — | ✓ |
| **pineapple** | 228210 | 229680 | ✗（1470 字节尾部 padding）|
| **zheng** | 138596 | 114242 | ✗（idx 取自更大存档）|

**只有 zheng 与 pineapple 不一致。** pineapple 的 idx 内部完全自洽（各段对齐、末值 ≤ 文件），多出的 1470 字节是未初始化填充（`cc cc cc` + UTF-16LE 残留 `00 56 00 58…`），不是真实数据——因此对 pineapple **保留出厂 idx** 即可。

## 7. 探测算法设计（数据驱动，不依赖 MOD 名）

对每个段（Person rec=182 名@8；Thing rec=190 名@2/名2@22/说明@42；Scene rec=52 名@2；Wugong rec=136 名@2）：

1. 扫描文件全部 Big5 串起点。
2. 对每个串，令 `start = pos − 字段偏移` 作为候选数组起点。
3. 在 `start` 处按 stride=rec 测量最长连续记录数（Thing 要求 3 个字段都在才算一条）。
4. 取最长 run 的起点作为该段起点。
5. 链式：段 i 的**结束** = 段 i+1 的**起点**（这正是 idx 的定义），避免一个数组的多余尾记录把后续段整体推后。
6. 末段结束 = 自身 run 长度；Shop 用剩余字节整数条补齐。

验证：对 zheng 精确得到 `836,59076,97076,101444,114092,114242`；对 pascal 也精确得到同一布局。
