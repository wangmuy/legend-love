# 方案对比与选型：MOD `ranger.grp` 布局/编码适配

> 回答四个问题：
> 1. 哪个方案对后续兼容和更新更友好？
> 2. B 能做长短不同的动态长度吗？
> 3. D 怎么区分数值区有值还是走了旁路？
> 4. D 对后续更新修改更方便吗？UTF-8 字符串能一起压缩吗？

## 0. 前提事实（已验证，非推测）

| 事实 | 证据 |
|------|------|
| `ranger.idx` **只有 6 个段偏移**，段内记录边界靠 `recsize` 推算 | `ranger.idx` = 24 字节 = 6×uint32 |
| 因此**段内记录必须定长**，否则 idx 无法描述 | 同上 |
| 引擎把整段读入**扁平字节缓冲**，字段按 `i*Size + 固定偏移` 访问 | `jymain.lua:1675-1705` |
| `Byte.setstr` 按字节写入，**到 length 就停**（且不写 NUL 终止符） | `framework/lib_Byte.lua` |
| 字符串字段**既读也写**，但只有 2 处写：主角姓名（≤4字）、主角居所名 | `jymain.lua:252`、`:193` |
| 每段 `代号` 唯一且连续 `0..n-1`（Shop 除外，无字符串） | 实测 20 MOD |
| 记录内**无空闲区**可原地加宽 | 逐字节扫描 Person 28..182、Thing 102..190 |

## 1. 四个方案的本质区别

```
                    ranger.grp 里的字符串    字符串存在哪        记录是否定长
A 仅原地转码        Big5 → UTF-8（原地）      仍在记录里          定长（截断）
B 加宽记录          Big5 → UTF-8（加宽字段）  仍在记录里          定长（但更宽）
C 运行时不转码      Big5（原样）              仍在记录里          定长
D 旁路字符串表      清零或原样                独立 UTF-8 表       定长
```

**关键：B 和 D 都不截断，区别是「字符串放记录里」还是「放记录外」。**

## 2. Q2：B 能做长短不同的动态长度吗？

**不能（在当前 `.idx` 格式下）。**

`ranger.idx` 只记录 6 个**段起点**，段内没有任何记录边界信息。引擎靠
`PersonNum = (idx[2]-idx[1]) / PersonSize` 反推记录数，再 `i*PersonSize` 定位第 i 条。
如果某条记录变长，后面所有记录的偏移全部错位，且引擎无从得知每条多长。

要做到变长，必须**同时改造 `.idx` 格式**：从「6 个段偏移」变成「每条记录一个偏移」
（类似 `talk.idx` 那种每行一个 offset 的格式）。这会：

- 破坏与原版 `.idx` 的兼容（同一个 `LoadRecord` 要分支处理两种 idx）
- 使 `LoadRecord` 的 `i*Size` 快速索引失效，改为查表
- 存档格式（`rN.idx`）也要跟着变，涉及既有存档兼容

所以 **B 只能是「定长但更宽」**。好消息是：只要宽度够（见下表），就足以容纳所有 MOD 的字符串。

| 字段 | MOD 现状 | Big5 最长 | 建议宽度 | UTF-8 可放 |
|------|---------|----------|---------|-----------|
| Person 姓名 | 10 | 5 字 | **16** | 5 字 ✅ |
| Person 外号 | 10 | 5 字 | **16** | 5 字 ✅ |
| Thing 名/名2 | 20 | 9 字 | **32** | 10 字 ✅ |
| Thing 说明 | 30 | 17 字 | **56** | 18 字 ✅ |
| Scene 名称 | 10 | 5 字 | **16** | 5 字 ✅ |
| Wugong 名称 | 10 | 6 字 | **20** | 6 字 ✅ |

**结论：B 不需要变长，只需要把定长字段加宽到足够。** 截断问题彻底消失。

## 3. Q3：D 怎么区分「数值区有值」还是「走了旁路」？

**不需要区分——因为两者的作用域完全不同。**

- **数值字段**（生命、攻击力…）：只从记录缓冲区读，**永远不看旁路表**
- **字符串字段**（姓名、物品说明…）：`GetDataFromStruct` 遇到 `t[2]==2` 时**只查旁路表**，**永远不看记录缓冲区**

即：`GetDataFromStruct` 里按字段类型**二选一**，不是「先看记录再看旁路」。所以不存在歧义。

```lua
-- 伪代码：改造后的 GetDataFromStruct
if t[2] == 2 then                      -- 字符串
    return SideStr[segName][recordIndex][fieldName]   -- 只查旁路
else                                    -- 数值
    return Byte.get16(data, t[1]+offset)              -- 只查记录
end
```

**key 的稳定性已验证**：每段 `代号` 唯一且连续 `0..n-1`，所以 `(段名, 记录下标, 字段名)`
三元组是无歧义主键。也可以直接用 `(段名, 记录下标)` 索引一张 `{姓名=..., 外号=...}` 子表。

**旁路表里记录缓冲区那段字符串怎么办？** 三种处理：
1. **保持原样 Big5**（最安全，缓冲区大小完全不变，数值偏移零风险）← 推荐
2. 清零（省不了空间，反而丢失信息，无意义）
3. 删除（会改变记录大小 → 破坏偏移，不可行）

推荐 (1)：缓冲区一字不改，只是引擎**不再从那里读字符串**。

## 4. Q4：D 对后续更新修改更方便吗？

**分场景看，答案是「看你怎么更新」：**

| 更新场景 | B（记录内） | D（旁路表） |
|---------|------------|------------|
| 改一个物品说明（换更长的文案） | ❌ 受字段宽度限制，超了要改布局 | ✅ 表里随便改，长度自由 |
| 新增一条记录 | ✅ 段尾追加定长记录 | ✅ 追加记录 + 追加表项 |
| 新增一个**字符串字段** | ❌ 要改记录布局 + 所有偏移 | ✅ 表里加一列，记录不动 |
| 数值字段调整 | ✅ 直接改 | ✅ 直接改（不受影响） |
| 与 UPedit 互操作 | ✅ 格式一致，UPedit 能直接编辑 | ❌ UPedit 读不到字符串（表是自造的） |
| 用文本编辑器/脚本批量替换文案 | ❌ 二进制里混着字符串，难定位 | ✅ 纯文本表，`grep`/`sed` 直接改 |
| 翻译/多语言 | ❌ 要动二进制 | ✅ 换一张表即可 |
| diff 可读性 | ❌ 二进制 diff 无意义 | ✅ 文本表 diff 清晰 |

**核心权衡**：
- **D 对「运行时/构建期的字符串维护」明显更友好**（文本化、长度自由、可 diff、可多语言）
- **B 对「与 UPedit 生态互操作」更友好**（格式就是 UPedit 的原生格式，MOD 作者改完能直接用）

> 注意：**两者对「引擎侧改动量」差不多**——都要在 `mod_data.lua` 加一张 MOD 布局表
> （B 是加宽的字段表，D 是 `{段→字段}` 的表 + 一个旁路表加载器）。

## 5. Q4 附：UTF-8 字符串能一起压缩吗？

**能，而且收益明显。** 实测 mingdong：

| 项 | 数值 |
|----|------|
| 字符串条数 | 2724 |
| Big5 总字节 | 23301 |
| **去重后** | **1397 条 / 13377 字节**（重复率 49%！） |
| UTF-8 估算 | ~34950 字节 |
| **zlib 压缩后** | **8957 字节** |

**结论：**
- **去重**：字符串重复率高达 49%（大量同名物品、同一外号），去重后直接省一半
- **zlib**：UTF-8 拼接后压缩到 8957 字节（约原始 UTF-8 的 1/4）
- 对比原始 `ranger.grp` 223688 字节，旁路表（压缩后）只有 ~9KB，**完全可忽略**

**压缩的代价**：需要解压步骤。但注意：
- 构建期可以**只去重、不压缩**（简单、可读、可 diff、~34KB），或**去重+zlib**（~9KB，不可读）
- 运行时解压一次到内存表，之后全走内存，**无运行时开销**
- 若追求可读性/可维护性，**建议只做去重 + 存纯文本**，把压缩留给需要时再加

## 6. 选型建议

| 你的优先级 | 推荐 |
|-----------|------|
| 与 UPedit 生态一致、MOD 作者能直接编辑、改动最小 | **B**（加宽定长） |
| 字符串好维护、可 diff、可翻译、长度自由、省空间 | **D**（旁路表 + 去重，可选 zlib） |
| 想两者兼得 | **B+D 混合**：记录内保留加宽字段（兼容 UPedit 读取），同时旁路表覆盖（供引擎优先使用）。代价是两份数据 |

**我的推荐：D（旁路表），理由：**
1. **不截断**（满足 Q3），且长度完全自由 —— 未来任何超长文案都不会再出问题
2. **数值区零改动** —— 记录缓冲区一字不改，所有数值偏移零风险，最安全
3. **可读可 diff** —— 纯文本表，`git diff` 能看清每次 MOD 更新改了什么文案
4. **体积小** —— 去重后 ~13KB，压缩后 ~9KB
5. **改动集中** —— 只在 `GetDataFromStruct`/`SetDataFromStruct` 加一个字符串分支

**D 的唯一缺点**：与 UPedit 二进制格式不再一致（UPedit 读不到我们的字符串）。
但考虑到：
- 我们**只读** MOD，不产出供 UPedit 编辑的文件
- 若要回写，随时能从旁路表重建 Big5 记录

这个缺点在实践中不构成障碍。

**若你更看重「未来 19 个 MOD 的批量处理稳定性」，B 也完全可行**（定长加宽，截断消失），
且与现有 `mod_build.lua` 的「保大小不变」策略差异最小。
