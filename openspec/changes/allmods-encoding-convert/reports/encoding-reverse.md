# MOD 存档/定义数据 编码与布局逆向报告（终版）

> Q1 逆向结论。**权威来源：`reference/allmods/UPedit/UPedit.ini` 的 `[R_Modify]` 段** —— 这是 MOD 编辑器 UPedit 自带的记录结构定义，直接给出了 allmods 格式的每个字段偏移与字节数。无需再靠推测。

## 1. 结论速览

1. **MOD 数据编码是 Big5**，引擎按 UTF-8 读 → 乱码。（已确认）
2. **MOD 记录布局与引擎内置的原版布局完全不同** —— 这才是更严重的问题。
3. **MOD 名称字段只有 10~20 字节**（Big5 可放 5~10 个汉字），转 UTF-8（3 字节/汉字）后只能放 3~6 个汉字 → **13104 个字段会被截断**，与 Q3「不能有内容截断或遗漏」直接冲突。
4. 因此 **必须同时做「布局适配」和「编码转换」**，且需要重新设计存储策略才能满足 Q3。

## 3. 编码转换的截断问题（Q3 核心冲突）
Big5 汉字 = 2 字节；UTF-8 汉字 = 3 字节。字段宽度固定 → 容量缩水到 2/3：

| 字段 | 字节 | Big5 容量 | UTF-8 容量 |
|------|------|----------|-----------|
| Person 姓名 | 10 | 5 字 | **3 字** |
| Person 外号 | 10 | 5 字 | **3 字** |
| Thing 物品名 | 20 | 10 字 | **6 字** |
| Thing 物品名2 | 20 | 10 字 | **6 字** |
| Thing 物品说明 | 30 | 15 字 | **10 字** |
| Scene 名称 | 10 | 5 字 | **3 字** |
| Wugong 名称 | 10 | 5 字 | **3 字** |

### 全 20 MOD 实测截断统计

| MOD | P姓名max | P外号max | T名max | T说明max | S名max | W名max | 截断字段数 |
|-----|---------|---------|--------|---------|--------|--------|-----------|
| kys-BookCalamity | 5 | 5 | 8 | 15 | 5 | 5 | **1333** |
| kys-awaken | 5 | 5 | 8 | 17 | 5 | 5 | **1246** |
| kys-mingdong | 4 | 5 | 8 | 15 | 5 | 5 | 976 |
| kys-Dragon | 5 | 5 | 8 | 14 | 5 | 5 | 962 |
| …（其余 16 个） | | | | | | | 197 ~ 656 |
| **合计** | | | | | | | **13104** |

**13104 个字段会被截断。** 这不是转换 bug，而是**格式固有**：MOD 作者用满了 Big5 的字段容量（如 5 字姓名、15 字说明），UTF-8 装不下。

### 无空隙可扩展

已逐字节验证：Person 记录 `28..182` 全部被数值字段占用（性别@28 … 携带物品4数量@180），Thing 记录 `102..190` 也被后续数值字段占用。**没有任何空闲区域可用于加宽字符串字段。**

## 4. 可选方案

| 方案 | 做法 | 满足 Q3？ | 代价 |
|------|------|----------|------|
| **A. 仅改编码（原地）** | Big5→UTF-8，字段宽度不变，超长截断 | ❌ 13104 处截断 | 低 |
| **B. 改编码 + 加宽字段 + 改记录布局** | 重写 `ranger.grp` 为「宽字段」布局（如姓名 20、外号 20、说明 60），同步覆盖 `CC.*_S`/`CC.*Size` 与 `ranger.idx` | ✅ 无截断 | 中高；需引擎侧布局表；文件变大 |
| **C. 运行时不转码，引擎按 Big5 读取** | 保留 Big5，在引擎侧做 Big5→UTF-8（渲染时） | ✅ 无截断 | 运行时开销；需 Big5 解码器进引擎 |
| **D. 旁路字符串表** | `ranger.grp` 数值部分保持原样，字符串抽出为独立 UTF-8 表（`ranger.str`），引擎按 id 查表 | ✅ 无截断 | 需改引擎读取路径；`ranger.grp` 中字符串区填空 |

## 5. 建议

**方案 B**：构建期把 MOD `ranger.grp` 重写为「UTF-8 宽字段」格式，并让 `mod_data.lua` 在 MOD 激活时覆盖记录布局常量。理由：

- 无截断、无遗漏（满足 Q3）
- 纯构建期完成，运行时零开销（优于 C）
- 布局仍由构建期固定，可验证、可回归
- 引擎侧只需一张「MOD 布局表」，改动集中

关键设计：构建期产出**新布局**的 `ranger.grp` + `ranger.idx`，布局为：

| 段 | rec | 字段 |
|----|-----|------|
| Person | 182 | 姓名@8+**16**（5字UTF-8上限15）、外号@18+**16** |
| Thing | 190 | 名@2+**32**、名2@22+**32**、说明@42+**48** |
| Scene | 52 | 名称@2+**16** |
| Wugong | 136 | 名称@2+**16** |

但**字段加宽会与后续数值字段冲突**（Person 28..182 已占满）。因此方案 B 实际需要**把记录整体加宽**（例如 Person 182→200，Thing 190→230），并重算 `ranger.idx` 与所有段偏移。

## 附录：CP950 扩展码位缺失（构建期 bug，已修复）

### 现象
`ranger.grp` 字符串字段中出现 U+FFFD（`�`）：
- 14/20 MOD 共 **87 个字段**受影响。
- 典型例子：mingdong `Person[21].Nick` = `恒山掌門`，首字被解码为 `�`。

### 根因
`game/tools/mod_big5_trad.lua` 由 **plain big5** 生成，缺少 **CP950 扩展码位 42 个**：

| 码位 | 字符 | 说明 |
|---|---|---|
| `0xf9d6` | 碁 | f9xx 扩展段 |
| `0xf9d7` | 銹 | |
| `0xf9d8` | 裏 | |
| `0xf9da` | **恒** | ← `恒山掌門` 的首字，最常触发 |
| `0xf9db` | 粧 | |
| `0xf9dc` | 嫺 | |
| `0xf9dd`–`0xf9fc` | ╔╦╗… | 制表符框线 |
| `0xa3e1` | € | 欧元符号 |

`0xf9da` 不是合法 Big5（Python `big5` codec 亦拒绝），但 **CP950 / Big5-HKSCS 可解码**。
MOD 数据由 Windows 编辑器（CP950 环境）产出，因此包含这些码位。

### 证据
```
原始字节: f9 da a4 73 b4 78 aa f9
plain big5 : UnicodeDecodeError
cp950      : '恒山掌門'      ← 正确
big5hkscs  : '恒山掌門'      ← 正确
```

### 修复
向 `mod_big5_trad.lua` 追加 42 个 CP950 码位（13710 → **13752** 条目）。
修复后：19/20 MOD 的 U+FFFD 归零；仅 `zheng` 残留 15 个（源数据布局损坏，见
`mod-test-guide.md` 第二节）。

### 影响范围
- **仅 `ranger.grp` 字符串字段**。talk 提取不受影响（全部 MOD 的 `talk.grp` 中 f9xx 出现 0 次）。
- 回归测试：`tests/unit/test_mod_data.lua` 的
  `testBig5TableCoversCp950Extensions` / `testDecodeBig5Cp950Extension`。
